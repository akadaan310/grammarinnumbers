## Five readings of $1 + 1$ {#sec:add-five}

1. **Counting.** Put one object next to another and count: the result is the count of the union. $|\{a\}| + |\{b\}| = |\{a, b\}|$ for distinct $a, b$.
2. **Successor.** By primitive recursion, $\mathrm{add}(1, S0) = S(\mathrm{add}(1, 0)) = S(1) = 2$: two rule applications (Chapter 4).
3. **Cardinality.** For disjoint finite sets, $|A \sqcup B|$ depends only on $|A|$ and $|B|$, because bijections $A \to A'$ and $B \to B'$ combine into a bijection $A \sqcup B \to A' \sqcup B'$. Addition *is* the operation induced on counts.
4. **Algebra.** In any ring, $1 + 1$ is the element $2$ of the subring generated by $1$. (In $\Z/2$ that element is $0$: the same expression, a different structure.)
5. **Machine.** In binary, the digit pair $(1, 1)$ produces sum bit $0$ and carry $1$; a half adder computes $\mathrm{XOR}(1, 1) = 0$ and $\mathrm{AND}(1, 1) = 1$, giving the word `10`.

That readings 1–3 agree is the content of the statement that $\N$ *is* the set of finite cardinalities, made precise by the recursion theorem: cardinality of a disjoint union and primitive-recursive addition are both functions $\N \times \N \to \N$ satisfying $f(m, 0) = m$ and $f(m, Sn) = S f(m, n)$, so they coincide. Reading 4 agrees with them in $\Z$ because $\Z$ contains $\N$ as its non-negative part, and disagrees in $\Z/2$ because $\Z/2$ is a quotient in which $2 = 0$. Reading 5 agrees with them *as long as the result is decoded with the base-2 denotation and fits in the available bits* — the two conditions that Chapter 26 shows to fail on machines.

Throughout, distinguish what is **invariant** (the value $2$), what is **generated** (a new position, the carry), and what is **merely represented** (the word `10` in base 2, `2` in base 10, `SS0` in unary).

## The column algorithm {#sec:column}

The algorithm taught in school adds two numerals digit by digit from the right, carrying when a column overflows. In base $b$, with digit lists $a_0, \ldots, a_{n-1}$ and $b_0, \ldots, b_{n-1}$ (least significant first, padded with zeros to equal length):

::: algorithm {#alg:column-add title="Column addition in base b"}
$c_0 \leftarrow 0$. For $i = 0, \ldots, n-1$: let $t = a_i + b_i + c_i$; set $s_i \leftarrow t \bmod b$ and $c_{i+1} \leftarrow \lfloor t / b \rfloor$. Finally $s_n \leftarrow c_n$. Output the digits $s_n s_{n-1} \cdots s_0$.
:::

::: proposition {#prop:column title="Correctness of column addition; the carry is at most 1" status="classical" ledger="GIN-PROP-057"}
For every $i$, $c_i \in \{0, 1\}$, and after column $i$
$$
\sum_{j=0}^{i} s_j b^j + c_{i+1}\, b^{i+1} \;=\; \sum_{j=0}^{i} (a_j + b_j)\, b^j . \label{eq:col-inv}
$$
At $i = n - 1$ this says that the output denotes $\val(a) + \val(b)$. The output has at most $n + 1$ digits.
:::

::: proof
*Carry bound.* $c_0 = 0$. If $c_i \le 1$ then $t \le (b - 1) + (b - 1) + 1 = 2b - 1$, so $c_{i+1} = \lfloor t/b \rfloor \le 1$. *Invariant.* By construction $t = s_i + b\, c_{i+1}$, i.e. $a_i + b_i + c_i = s_i + b\, c_{i+1}$. Multiply by $b^i$ and add to the invariant for $i - 1$ (which holds trivially for $i = -1$ with the empty sum and $c_0 = 0$): the term $c_i b^i$ cancels, leaving \eqref{eq:col-inv}.
:::

The invariant is the precise content of "carrying the one": the carry is a deferred contribution of exactly $b^{i+1}$, and the algorithm never loses it. The carry bound explains why one bit of memory between columns suffices in *any* base — a fact we will use in Chapter 11 to show that addition is a finite-state computation.

```python run
def column_add(a, b, base=10):
    A, B = [int(d, base) for d in reversed(a)], [int(d, base) for d in reversed(b)]
    n = max(len(A), len(B)); A += [0] * (n - len(A)); B += [0] * (n - len(B))
    c, s, rows = 0, [], []
    for i in range(n):
        t = A[i] + B[i] + c
        s.append(t % base); rows.append((i, A[i], B[i], c, t % base, t // base)); c = t // base
    s.append(c)
    return "".join("0123456789abcdef"[d] for d in reversed(s)).lstrip("0") or "0", rows

for a, b, base in [("1", "1", 2), ("1", "1", 10), ("999", "1", 10), ("1011", "111", 2)]:
    out, rows = column_add(a, b, base)
    print(f"{a} + {b} (base {base}) = {out}   carries out: {[r[5] for r in rows]}")
```

```output
1 + 1 (base 2) = 10   carries out: [1]
1 + 1 (base 10) = 2   carries out: [0]
999 + 1 (base 10) = 1000   carries out: [1, 1, 1]
1011 + 111 (base 2) = 10010   carries out: [1, 1, 1, 1]
```

## The cost of addition {#sec:add-cost}

Column addition of two $L$-digit numerals performs $L$ column steps, each a bounded amount of work on digits: $\Theta(L)$ digit operations. In base $2$, that is $\Theta(L)$ bit operations; in base $2^{32}$ (machine words, "limbs"), $\lceil L / 32 \rceil$ add-with-carry instructions.

::: proposition {#prop:add-lower title="Addition cannot be done in sublinear time on numerals" status="classical" ledger="GIN-PROP-058"}
Any algorithm that computes the binary numeral of $x + y$ from the binary numerals of $x$ and $y$ (each of length $L$) must read all $2L$ input bits in the worst case. Hence addition costs $\Theta(L)$ bit operations, and column addition is optimal up to a constant factor.
:::

::: proof
For any position $i$ and any choice of the other bits with $y = 0$, flipping bit $i$ of $x$ flips bit $i$ of the sum; so an algorithm that does not read bit $i$ of $x$ outputs the same bit $i$ for two inputs whose sums differ there. The same argument applies to $y$. The output itself has $\Theta(L)$ bits, which also bounds the cost from below.
:::

Two remarks prevent misreading the proposition. First, it is about *sequential* reading of numerals. With many processors working at once, all bits can be read in parallel, and addition can be done in time $\Oh(\log L)$ — by computing all carries simultaneously, as Chapter 11 explains. Second, it says nothing about machine words: adding two numbers that fit in one 64-bit register is *one* instruction. "Addition is $\Oh(1)$" and "addition is $\Theta(L)$" are both true, of different models (\chapref{36-cost-models}).

The SDK's limb arithmetic counts the work explicitly:

```python run
from ginsdk import bigint
from ginsdk.cost import Cost

for bits in (64, 1024, 16384):
    x, y = (1 << bits) - 1, (1 << bits) - 3
    c = Cost()
    s = bigint.add(bigint.from_int(x), bigint.from_int(y), c)
    assert bigint.to_int(s) == x + y
    print(f"{bits:6d}-bit operands: {c['add']:4d} limb additions (32-bit limbs), result {len(s)} limbs")
```

```output
    64-bit operands:    2 limb additions (32-bit limbs), result 3 limbs
  1024-bit operands:   32 limb additions (32-bit limbs), result 33 limbs
 16384-bit operands:  512 limb additions (32-bit limbs), result 513 limbs
```

## Adding rationals {#sec:add-rationals}

Rationals are classes of pairs (Chapter 9), and their sum is defined on representatives:
$$
\frac{a}{b} + \frac{c}{d} = \frac{ad + bc}{bd} .
$$
The definition is well posed — replacing $(a, b)$ by $(ka, kb)$ multiplies numerator and denominator of the sum by $k$ — but it does not return a *canonical* representative: $\tfrac{1}{6} + \tfrac{1}{3} = \tfrac{9}{18}$, which must be reduced to $\tfrac{1}{2}$ by dividing by $\gcd(9, 18) = 9$. Exact rational arithmetic therefore pays, on every addition, for three multiplications and a gcd, and its operands can grow: the sum of $n$ unit fractions $1/k$ has a denominator that grows exponentially in $n$. Rational addition is exact and total on $\Q$; it is not cheap.

## Adding floating-point numbers {#sec:add-float}

IEEE 754 defines floating-point addition as exact addition followed by *one* rounding to the format: $x \oplus y = \rnd(x + y)$ (\chapref{25-floating-point}). Commutativity survives, because $x + y = y + x$ before rounding. Associativity does not:

::: counterexample {#neg:float-assoc title="Floating-point addition is associative" status="counterexample" ledger="GIN-NEG-001"}
In binary64, $(0.1 + 0.1) + 0.4 = 0.6000000000000001$ but $0.1 + (0.1 + 0.4) = 0.6$. Of the $729$ triples of one-digit tenths $(0.1, \ldots, 0.9)^3$, $242$ give different results under the two groupings (\ledger{GIN-PROP-032}).
:::

```python run
from ginsdk import evaluate

for e in ["(0.1 + 0.1) + 0.4", "0.1 + (0.1 + 0.4)", "(1e16 + 1) - 1e16"]:
    e2 = e.replace("1e16", "10000000000000000")
    print(f"{e:20s} binary64: {evaluate(e2, 'binary64').display:22s} exact: {evaluate(e2, 'Q').display}")
```

```output
(0.1 + 0.1) + 0.4    binary64: 0.6000000000000001     exact: 3/5
0.1 + (0.1 + 0.4)    binary64: 0.6                    exact: 3/5
(1e16 + 1) - 1e16    binary64: 0                      exact: 1
```

The third line is *absorption*: $10^{16} + 1$ is not representable in binary64 (the spacing of representable numbers near $10^{16}$ is $2$), so the $1$ is lost entirely. Addition of floating-point numbers is total, commutative and correctly rounded, and it is not the addition of the real numbers it approximates.

::: exercise {#ex:add-base3}
Add $2121_3$ and $1012_3$ with Algorithm \ref{alg:column-add}, listing the carries. Check by converting to decimal.
:::

::: solution {of="ex:add-base3"}
Columns from the right: $1 + 2 = 3 = 10_3$: digit $0$, carry $1$; $2 + 1 + 1 = 4 = 11_3$: digit $1$, carry $1$; $1 + 0 + 1 = 2$: digit $2$, carry $0$; $2 + 1 = 3$: digit $0$, carry $1$. Result $10210_3$. Check: $2121_3 = 70$, $1012_3 = 32$, $10210_3 = 81 + 0 + 18 + 3 + 0 = 102$. ✓
:::

::: exercise {#ex:add-carry-bound}
Show that if three numerals are added column by column in base $b$, the carry never exceeds $2$. What is the bound for $k$ numerals?
:::

::: solution {of="ex:add-carry-bound"}
With carry $c \le 2$, a column sum is at most $3(b - 1) + 2 = 3b - 1$, so the next carry is at most $2$. For $k$ numerals, if $c \le k - 1$ the column sum is at most $k(b - 1) + k - 1 = kb - 1$, so the carry stays at most $k - 1$.
:::

::: exercise {#ex:add-z2}
Which of the five readings of §\ref{sec:add-five} give $1 + 1 = 0$, and in which structure?
:::

::: solution {of="ex:add-z2"}
The algebraic reading in $\Z/2$ (and the machine reading in a one-bit register that discards the carry, which is $\Z/2$ again). Counting, successor and cardinality readings all live in $\N$, where $1 + 1 = 2 \ne 0$.
:::

::: exercise {#ex:add-harmonic}
Compute $\sum_{k=1}^{20} 1/k$ exactly with `fractions.Fraction` and report the number of digits of the reduced denominator. What does this say about the cost of exact rational addition?
:::

::: solution {of="ex:add-harmonic"}
$H_{20} = 55835135/15519504$; the reduced denominator has $8$ digits and equals $\mathrm{lcm}(1, \ldots, 20)/15$. The denominators grow like $\mathrm{lcm}(1..n) \approx e^{n}$, so operand sizes — and therefore the cost of each further addition — grow linearly in $n$ bits.
:::

::: summary
- Counting, successor, cardinality, algebra and machine define $1 + 1$; they agree in $\N$ by the recursion theorem, and the machine reading agrees only within its encoding and width.
- Column addition is correct by an explicit invariant; the carry is at most $1$ in every base.
- Addition of $L$-bit numerals costs $\Theta(L)$ bit operations and no sequential algorithm does better; on bounded machine words it is one instruction.
- Rational addition is exact but needs a gcd to stay canonical; floating-point addition is commutative, correctly rounded, and not associative.
:::
